# 首页实时请求流需求文档

**需求编号**: REQ-2026-07-03-001  
**提出时间**: 2026-07-03  
**需求状态**: 待评审  
**优先级**: P1（核心功能）

---

## 一、需求背景

当前仪表盘采用定时轮询方式（15-30秒间隔）获取统计数据，无法实时展示请求流动态。运维人员需要更直观的实时监控能力，以便快速发现异常、评估系统负载、观察模型选择分布。

---

## 二、核心需求

### 2.1 实时请求流可视化

在首页仪表盘顶部增加**横向泳道组件**，实时展示请求流：

#### 2.1.1 视觉呈现
- **布局**: 横向泳道，从右向左推进（类似 Grafana 时序图）
- **容量**: 同时显示 100 个请求块（固定窗口），超出的自动挤出左侧
- **初始加载**: 默认加载最近 50 条请求，按时间正序排列（从左到右）
- **空闲标记**: 若 1 分钟内无新请求，推入一个**空心占位块**作为时间间隔标记

#### 2.1.2 请求块设计
每个请求用一个**分层色块**表示，分为上下两部分：

**上半部分 - 模型标识**
- 背景色：根据模型分类着色（见下方图例）
- 显示：模型简称（如 `GPT-4o`, `Claude-3.5`）
- 鼠标悬停：显示完整模型名 + 供应商

**下半部分 - 状态与耗时**
- 背景色：根据状态着色
  - 🟢 成功 (success): `#22c55e` (绿色)
  - 🟡 进行中 (in_progress): `#f59e0b` (橙色)
  - 🔴 失败 (failure): `#ef4444` (红色)
- 显示：响应时长（如 `1.2s`, `320ms`）
- 鼠标悬停：显示详细状态信息（错误类型、token 数、成本）

**空闲占位块**
- 大尺寸空心矩形（宽度约为普通请求块的 2 倍）
- 边框：虚线，颜色 `#d1d5db`
- 内部显示：`1 min idle` 或相对时间戳

#### 2.1.3 图例（Legend）
在泳道组件下方或右侧展示：

**模型分类色卡**（可折叠）
- 🔵 OpenAI 系列: `#3b82f6` (蓝色)
- 🟣 Anthropic 系列: `#8b5cf6` (紫色)
- 🟠 国产模型: `#f97316` (橙色)
- 🟢 开源模型: `#10b981` (青绿色)
- ⚪ 其他/未分类: `#6b7280` (灰色)

**状态色卡**
- 🟢 成功 | 🟡 进行中 | 🔴 失败

### 2.2 实时数据更新

#### 2.2.1 仪表盘统计卡增量更新
当 WebSocket 推送新请求时，**实时增量更新**以下统计卡（无需重新请求 API）：

- **总请求数** (`total_requests`) +1
- **总 Token 数** (`total_tokens`) += (prompt_tokens + completion_tokens)
- **总成本** (`total_cost_usd`) += cost_usd
- **成功率** (`success_rate`) 重新计算 = success_count / total_count
- **平均延迟** (`avg_latency_ms`) 滚动平均更新

#### 2.2.2 增量计算规则
- 仅对**当前选择的时间范围**内的请求进行累加（如最近 7 天）
- 使用客户端缓存队列（FIFO），超出时间窗口的旧记录自动剔除
- 每 5 分钟与后端全量数据校准一次，防止漂移

---

### 2.3 交互能力

#### 2.3.1 点击请求块
- 弹出抽屉式详情面板（复用现有 `/api/logs/{request_id}` 接口）
- 显示完整请求日志（request_body, response_body, 路由决策等）

#### 2.3.2 过滤与控制
- **暂停/播放按钮**: 暂停时停止推送动画，但后台继续缓存
- **速度控制**: 慢速（2x）/ 正常（1x）/ 快速（0.5x） 动画速度
- **模型筛选**: 多选下拉框，仅显示选中模型的请求
- **状态筛选**: 全部 / 仅成功 / 仅失败

## 三、需求优化建议

### 3.1 原需求改进点

| 原始表述 | 潜在问题 | 优化方案 |
|---------|---------|---------|
| "从右向左推进来" | 未说明初始加载顺序 | 初始加载从左到右正排，新请求从右侧追加 |
| "1分钟没有请求推空色块" | 空色块缺少视觉层次 | 改为大尺寸虚线空心块，带相对时间标记 |
| "下半部是状态与时间长度" | 表述模糊 | 拆分为：状态色 + 响应耗时显示 |
| "合理安排" | 缺少具体设计 | 提供详细色卡 + 尺寸规范 + 交互定义 |
| "增量计算" | 未说明如何避免误差累积 | 增加定期校准机制（5 分钟） |

### 3.2 技术可行性评估

✅ **可行点**
- 项目已有 `request_logs` 表和完整日志 API
- Vue 3 + Composition API 适合实时数据流管理
- Chart.js 可用于流式图表渲染
- Go 的 `gorilla/websocket` 成熟稳定

⚠️ **风险点**
1. **高并发场景**: 若 QPS > 100，前端动画可能卡顿
   - **缓解**: 采用批量推送（100ms 聚合窗口）+ 虚拟滚动
2. **WebSocket 重连**: 断线后如何补齐缺失的请求
   - **缓解**: 重连时携带 `last_seen_ts`，后端返回增量数据
3. **跨租户隔离**: 租户管理员仅能看到自己租户的请求
   - **缓解**: WebSocket 连接时验证 JWT，过滤推送数据

## 四、非功能需求

### 4.1 性能要求
- 前端动画帧率 ≥ 30 FPS（即使 QPS=50）
- WebSocket 消息延迟 < 500ms（P99）
- 单连接内存占用 < 5MB

### 4.2 兼容性
- 支持浏览器: Chrome 90+, Firefox 88+, Safari 14+, Edge 90+
- 移动端响应式适配（泳道改为竖向滚动）

### 4.3 可访问性
- 所有色块需有 `aria-label` 描述
- 支持键盘导航（Tab 切换请求块）
- 色盲友好：状态用图标 + 颜色双重标识

## 五、验收标准

### 5.1 功能验收
- [ ] 实时请求流组件在首页正常渲染
- [ ] 新请求到达时，从右侧推入，左侧旧请求被挤出
- [ ] 空闲 1 分钟后出现占位块
- [ ] 点击请求块弹出详情抽屉
- [ ] 统计卡数据实时增量更新，误差 < 5%
- [ ] 定期校准后误差归零

### 5.2 性能验收
- [ ] QPS=50 时前端无卡顿（Chrome DevTools FPS 监控）
- [ ] WebSocket 断线后 3 秒内自动重连
- [ ] 重连后补齐缺失请求（通过 `last_seen_ts` 查询）

### 5.3 安全验收
- [ ] 租户管理员仅能订阅自己租户的请求流
- [ ] WebSocket 连接需 JWT 鉴权
- [ ] 敏感字段（API key 完整值）不通过 WebSocket 传输
